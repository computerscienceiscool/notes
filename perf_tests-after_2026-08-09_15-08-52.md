## The four runs — what each measures, and WHY it is done

- **cold** — `goscalelint ./perf/...` on freshly generated code the tool
  has never seen. Nothing is cached, so it pays for everything: loading
  the package, parsing, type-checking, running all 17 analyzers, and
  printing findings.
  *Why:* establishes the worst case — what a first CI run on a fresh
  checkout feels like. Single sample by nature: code is only new once.
- **warm** — the exact same command immediately again (median of 5
  runs). The standalone binary keeps no results between runs, so all
  analysis happens again; only the surrounding I/O is cheaper (OS page
  cache, Go build cache).
  *Why:* proves the standalone path has NO result cache — warm stays
  expensive at scale — and the cold−warm gap isolates one-time setup
  cost from the analysis itself. Warm is the binary's floor for
  repeated runs.
- **vet 1st** — `go vet -vettool=goscalelint ./perf/...`: Go's vet
  command driving the same analyzers through the build system, on a
  cache miss (the build cache was cleared and the package is new).
  *Why:* measures the true analysis cost along the deployment path real
  CI uses — go/analysis tools are normally run via `-vettool`, not by
  invoking the binary directly. Single sample: a cache miss only
  happens once per package content.
- **vet 2nd** — the same vet command repeated (median of 5 runs).
  vet stores each package's results in the build cache keyed by content
  hash, so an unchanged package replays the stored diagnostics.
  *Why:* measures what every subsequent run on unchanged code costs —
  the state most CI runs are actually in. The vet1−vet2 gap is the
  payoff of caching, and a slow vet 2nd would be a red flag: it would
  mean the cache is not working (nondeterministic output or unstable
  input).

The columns work as pairs: cold vs warm separates setup from analysis;
vet 1st vs vet 2nd separates analysis from cache replay. Practical
reading: the standalone binary re-pays full analysis cost on every run,
while vet only pays for packages that changed — use `go vet -vettool`
for repeated runs (CI, hooks), the direct binary for one-shot scans.
